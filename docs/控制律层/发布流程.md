# 发布流程

本文件记录项目当前标准的 tag 发布流程，供维护者和协作 Agent 核对；发布操作由用户或维护者执行。

## 当前标准

- tag 发布默认通过 `.changelogs/<tag>.md` 覆盖 GitHub 自动生成的 release 正文。
- release 标题由 workflow 在 `gh release create --title` 创建 Release 时直接设置为 tag 名，例如 `5.0.15`。
- 若不存在对应覆盖文件，release workflow 会回退到 GitHub `generate-notes` 自动生成说明。
- 覆盖文件必须存在于 tag 指向的那次提交中，不能在 tag 推送后补写。
- `gradle/gtnh-baselines.json` 是受支持 GTNH manifest 与预期 GregTech 版本的唯一机器清单；`gradle.properties` 的 `elytra.manifest.version` 是默认开发与唯一出包基线的权威，不在清单中另设 default。
- tag 前必须由 `.github/workflows/branch-ci.yml` 从清单生成双基线 matrix；每项在独立只读 clean runner 上依次通过 `setupCIWorkspace`、精确依赖断言、`test`、`check`、`build`，稳定聚合门 `build` 阻断 plan 或任一基线失败。
- 每个 5.2 patch 候选的 branch CI 仅在 `baseline` job 由 runner 声明与拟发布 tag patch 一致的
  `VERSION=X.Y.Z-ci+${{ github.sha }}`；当前开发 CI 使用 `VERSION=5.2.0-ci+${{ github.sha }}`。
  每个 matrix leg 构建后都以 Python 标准库精确核对 generated `Tags.VERSION` 与主 JAR `Tags.class`；
  两个 baseline 对同一 SHA 必须得到同一合法 5.2 dev 版本。
- tag workflow 在 checkout、构建和 Release 副作用前通过 GitHub API 强制要求 `branch-ci.yml` 对 tag 的同一 SHA 存在 `push` 且 `success` 的运行；tag 早于 branch CI 时按预期 fail-closed，不等待、不跳过。
- tag workflow 仅使用 `gradle.properties` 指定且在清单中唯一命中的默认 manifest 构建，不为其他基线拆包；GitHub Release 创建失败会直接失败，也不会删除既有同名 Release。可选外部平台仍保持既有宽容策略。
- tag 后的 GitHub Release 与 assets 是独立发布结果，须另行核验，不能反向替代 JitPack 制品矩阵或 tag 前 branch CI。

## 标准步骤

1. 确认待发布代码已经完成本地授权验证，工作区干净；本地 `verify-gtnh-baselines.ps1` 仅为维护者可选诊断，不是发布权威且不授权 agent 执行。身份或工作区不符合预期即停止。
2. 在仓库根目录创建或更新 `.changelogs/<tag>.md`，并将覆盖文件与全部发布准备修改一起提交，形成完整候选提交；确认候选 tree 包含覆盖文件且工作区干净，否则停止。
3. 推送候选分支，等待 `branch-ci.yml` 对该 candidate exact SHA 的 `push` 运行完成；确认完整清单 matrix 各 leg 的 workspace setup、精确 GregTech 断言、test、check、build、5.2 generated/JAR 版本断言与聚合门均成功。缺少 exact-SHA 运行、仅有 PR 运行或任一步失败都停止。
4. 若版本依赖 Qz-UILib，按[《JitPack 发布依赖边界》](../反馈层/决策/jitpack-release-dependencies.md)执行 channel-aware 门禁。当前 JitPack 组合发布通道要求 Build API 为 `ok` 且 tag、public 仓库身份、commit 正确；非 `www`、无 query 的 canonical POM、main jar、实际 `dev` classifier jar、`sources` jar 及其校验和均返回真实目标内容，并由 clean consumer 以显式 `:dev` 坐标解析成功。该通道 `.module` 返回 `404` 是预期，不得套用普通 Maven Gradle Module Metadata 通道的 `.module=200` 规则；Maven Local、带 query/`www` 的旁路 URL、GitHub Release assets 或 GTNH Maven 状态均不能替代门禁。任一必需证据缺失或失败即停止。
5. 刷新目标主线并确认其身份未漂移，再使用 `git merge --no-ff` 合入完整候选；冲突、意外提交或无法保留显式 merge commit 时停止。确认 merge tree 含候选发布准备后推送主线，否则停止。
6. 等待 `branch-ci.yml` 对该 merge exact SHA 的 `push` 运行完成，并逐项满足步骤 3 的全部门禁；candidate SHA 的成功运行不能替代 merge SHA，缺失或失败即停止且不得创建 tag。
7. 再次确认同名 tag 与 Release 不存在，只在已通过步骤 6 的 merge commit 上创建 annotated tag；核对 tag object 与 peeled merge commit，身份不符即停止，不得使用 lightweight tag。
8. 推送 tag 并等待 `release-tags.yml`；exact-SHA 门无匹配或 workflow 的 checkout、setup、默认基线断言、assemble、GitHub Release 任一步失败都停止，不得绕过或提前手工创建 Release。
9. workflow 结束后独立核验 tag 指向、Release 标题/正文与预期 jar assets；可选外部平台的宽容步骤不能作为其真实发布证据，任一必需结果缺失时发布状态保持 **INCOMPLETE**。

## Qz-UILib 依赖门禁

- 权威坐标：`com.github.QuanhuZeYu:Qz-UILib:<tag>:dev`，仓库为 `https://jitpack.io`。
- 当前活动版本为 `4.6.3:dev`；JitPack 组合发布证据包括 API 身份、POM/main/`dev`/`sources` 内容与校验和及 clean consumer，`.module=404` 为该通道预期结果。
- 主动发布 GTNH Maven / GTNH releases 不是 Miner 发布前置，不要求 Maven 凭据；其制品可以是镜像，但不能取代 JitPack 权威验收。
- 目标 tag 不得移动。JitPack 的确定性缺陷应在新提交修复并发布新 tag，再重新核验完整制品矩阵。
- JitPack 失败须按源码、脚本、wrapper 权限与 runner 外部网络分别归因；跨域 `Temporary failure in name resolution` 不能误写成缺仓库或源码失败。
- 同一制品在 origin、不同 CDN 边缘、`www` 或带 query URL 的结果可能暂时不同；发布门只认上述 canonical 普通 GET，不以旁路命中绕过陈旧边缘。

## 覆盖文件规则

- 目录固定为 `.changelogs/`。
- 文件名必须与 tag 名完全一致，例如：`5.0.15` 对应 `.changelogs/5.0.15.md`。
- 文件内容使用 Markdown，作为 GitHub Release 正文直接发布，不负责 release 标题。
- 建议至少包含：本次更新、兼容性说明、验证结果。

## 命令示例

```bash
git add .changelogs/<tag>.md <其它发布准备文件>
git commit -m "[Chore]: 准备 Qz-Miner <tag> 发布"
git push origin <候选分支>
# 停止并等待 candidate exact-SHA branch CI 成功，再完成依赖门禁。
git fetch origin 5.0重构
git switch 5.0重构
git merge --ff-only origin/5.0重构
git merge --no-ff <candidate-sha> -m "[Merge]: 合入 Qz-Miner <tag> 发布候选"
git push origin 5.0重构
# 停止并等待 merge exact-SHA branch CI 成功。
git tag -a <tag> <merge-sha> -m "[Release]: Qz-Miner <tag>"
git push origin <tag>
# 等待 tag workflow，再独立核验 Release 正文与 assets。
```

## 注意事项

- 若 tag 已存在且对应提交中没有覆盖文件，本次 workflow 不会自动读取后补的 changelog。
- 覆盖文件不控制 release 标题；workflow 在 `gh release create --title` 创建 Release 时直接将标题设为 tag 名，不存在发布后统一改写步骤。
- 若需要完全手工控制单个版本的 release 内容，优先更新对应 `.changelogs/<tag>.md`，而不是修改 workflow。
- 若未来要调整自动生成策略，应同步检查上游复用的 `release-tags.yml` 与本文件是否一致。
- GitHub tag、Release、CI 或 Release assets 成功不等于对应发布通道的门禁已通过；任一必需证据未通过均暂停 Miner 发布。
- branch CI 通过也不等于 tag 后 Release/assets 已创建；两者分别在 tag 前、tag 后核验。CI matrix 的运行证据只能在 push 后取得，本地验证不得伪报为 CI 证据。
- 本地未显式注入时，Git-derived core 仍可能来自最近 tag，而不等于当前拟发布 patch；这种本地 build
  不得写成当前 5.2 patch artifact 证据。agent 不设置 `VERSION`，也不使用 Maven Local、`flatDir`
  或 URL 旁路伪造 5.2/Qz-UILib 制品可消费性。
- 5.2 family 的兼容冻结与升 minor 条件见
  [`network-version-compatibility.md`](../反馈层/决策/network-version-compatibility.md)；真实 mixed/missing
  client/dedicated 未完成时永久显式记为 **INCOMPLETE**，不由 CI/tag/Release 替代。
