# 跨会话交接模式

> 本文件定义**跨会话工作记忆**的转储与衔接规范。
> AGENTS.md 控制律层·Subagent 编排指向本文件与 `SUBAGENT-ORCHESTRATION.md`（同目录）。
> 目的：在上下文压缩前主动停会话，结构化保留必要信息，避免自动压缩导致的幻觉与注意力稀释。

## 1. 为什么需要这套

长任务跨多会话时有两个敌人：

- **注意力稀释**：上下文越大，模型对早期关键事实的注意力越弱
- **压缩幻觉**：系统自动压缩会丢信息、会臆造，且压缩点不可控

对策不是"记得更多"，而是**在用户掌控的时机主动停会话**，把工作记忆结构化落盘，开新会话冷启动核对后续接。核心原则：**主动停优于被动压缩，结构化优于自由总结，核对优于记忆**。

## 2. 与 `交接.md` 的边界

两个层次的状态，不可混：

| 层次 | 载体 | 寿命 | 装什么 |
|---|---|---|---|
| 项目状态 | `docs/反馈层/交接.md` | 跨多任务、长期 | 项目当前在哪（分支/HEAD/未收敛项/待拍板） |
| 会话工作记忆 | `.opencode/session-handoff.md` | 单任务内、易失 | 本会话干到哪（五层转储，任务完成即清理） |

会话 handoff **不替代**交接.md：任务完成后，handoff 中"有持续价值的事实"才回流到项目层（决策/错误预防/交接.md 的未收敛项），其余丢弃。

## 3. 何时触发停会话

**触发权在用户**，主 agent 不擅自断会话。两类信号：

- **用户主动停**：用户说"停"/"保留"/"开新会话"/"先记下来"——主 agent 立即执行五层转储
- **主 agent 提醒**：上下文较大（如长任务、多轮闭环后），主 agent 用中文 question 提醒"建议停会话做交接"，由用户拍板

阈值不写死（依模型上下文窗口与任务复杂度），由用户掌握。经验：上下文用到窗口的 10%-20% 时，注意力已开始稀释。

## 4. 停会话标准动作（五层转储）

用户触发后，主 agent 把当前会话的工作记忆按控制论五层写入 `.opencode/session-handoff.md`（覆盖式，模板见同文件）：

| 层 | 转储什么 |
|---|---|
| 设定值 | 任务合同版本；目标 / 非目标；验收、验证方法及必需性；边界与保护对象；自主权限；升级条件；对齐的宪章条目（I?）；可逆假设与未验证项；未决用户决定 |
| 传感 | 已探明的代码事实清单（`file:line`）、外部调研结论与来源 |
| 控制律 | 已执行改动（哪些文件改了什么）、闭环进度（规划/实施/复审到哪） |
| 纠偏 | 踩过的坑、被否决的方案及原因、返工点 |
| 反馈 | 待验证项（真机/测试）、待回写文档、下一步动作 |

**丢弃清单**（不进 handoff，它们是过程噪声）：

- 工具调用的原始输出（大块文件内容——新会话要读自己读）
- 已完成且无后续价值的中间过程
- 无教训价值的失败尝试（有教训的归"纠偏"层）

派发过的子 agent task 必须登记状态。跨会话不得保留任何可调用的旧 `task_id`；旧 ID 只能作审计标识，逻辑任务谱系及恢复预算继续传递。

### 4.1 任务记录与恢复

每条跨会话 task 记录统一使用字段：`prior_task_id|agent|goal|scope|state|attempts|last_evidence|remaining_action|successor`。

- `state` 必须来自 `NEW`、`RUNNING`、`COMPLETED`、`INTERRUPTED`、`TIMEOUT`、`INCOMPLETE`、`FAILED`、`UNKNOWN`；缺状态按 `UNKNOWN` 处理。
- `prior_task_id` 若存在只能填写 `<旧 ID>: AUDIT ONLY / DO NOT PASS`；主会话结束后不论状态均不得将其传给 Task 工具。
- `successor` 只能填写 `NEW TASK WITHOUT OLD TASK_ID`、等待用户或结束。可恢复态在新会话创建后继 task，并将派发计入同目标/角色/范围谱系的下一次恢复尝试；已消耗次数跨会话继承，只有实质改变方案、目标或范围才建立新谱系。
- `COMPLETED`、`FAILED`、`UNKNOWN`/缺状态仍是终态。审查不通过仍是 `COMPLETED`，返工必须登记为新的 fixer task。

## 5. 开新会话标准动作（冷启动核对）

新会话第一件事不是"凭 handoff 继续"，而是**先核对再续接**：

1. 读 `.opencode/session-handoff.md` + `docs/反馈层/交接.md` + `docs/控制律层/编排模式/SUBAGENT-ORCHESTRATION.md`
2. **核对 handoff 中的 `file:line` 仍有效**（代码可能已变，或 handoff 本身有幻觉）——抽检关键引用
3. 核对任务合同与权威事实是否漂移，并确认是否出现用户保留决策
4. 若无漂移且无用户保留决策，向用户复述"我接续到 X，下一步做 Y"后自动推进，不强制等待确认
5. 若发现漂移、错误或用户保留决策，先修正 handoff，并按任务合同集中询问后再续，不将错就错

## 6. 防幻觉铁律

- **handoff 也是模型产出，本身可能幻觉**：关键事实（路径/行号/不变量条目）在新会话必须重新核对，不凭 handoff 字面续接
- **不依赖模型记忆**：任何关键状态若不在 handoff 或权威文档里，视为丢失，不凭"印象中"继续
- **显式标注不确定性**：handoff 里不确定的事实标 `待验证`，新会话优先核对这些
- **自动压缩是最后防线，不是策略**：宁可主动停，不等系统压缩

## 7. 衔接纠偏

新会话发现衔接失败（信息遗漏/错误/过期）时：

- 当场补齐，不阻塞推进
- 同类衔接失误第 2 次出现——回看本模式文档第 4 节五层模板是否漏了某类信息，按需补条目（上溯规则同错误预防）
- 衔接失误的根因若属于"某类信息总被遗漏"，沉淀一条通则到本文件，不堆积个案

## 8. 与编排的关系

本模式是 `SUBAGENT-ORCHESTRATION.md` 的**时间维延伸**：编排文档管"同一会话内主 agent 如何调度子 agent"，本文件管"跨会话如何保住工作记忆"。两者共同支撑长时自动化任务——编排让单会话能扛复杂度，交接让多会话能扛时长。

## 9. 任务完成强制清理（防流水账）

会话工作记忆是**易失载体**，任务完成后必须走清理 checklist，防止 vibe coding 常见的"handoff 沉淀成流水账"。清理动作是硬性的，不是"建议"。

### 清理 checklist（任务完成后逐项过）

- [ ] **无持续价值的中间过程已丢弃**：工具原始输出、已完成无后续的尝试、无教训的失败——这些本就不该进 handoff，任务完成时确认它们没残留
- [ ] **回流项已逐条反向举证**：每条打算回流到项目层（决策/错误预防/交接.md 未收敛项）的事实，必须答上"持续价值三问"（见下），答不上就丢
- [ ] **session-handoff.md 已处理**：任务全完成→删除无持续价值的记录并回到模板初始态；尚有后续会话→仅保留逻辑任务与旧 ID 审计记录，旧 ID 标记 `AUDIT ONLY / DO NOT PASS`，后继标记 `NEW TASK WITHOUT OLD TASK_ID`，并继承谱系恢复预算
- [ ] **门禁已跑**：`powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-doc-discipline.ps1` 通过（handoff 不入 git、无流水账命名）

### 持续价值三问（回流反向举证）

每条要回流到项目层的事实，逐条回答，三问全过才回流：

1. **它会指导未来哪个决策？**（说不出具体场景 = 无持续价值，丢）
2. **它属于哪个控制层、应写回哪个权威文档？**（说不出归属 = 还没想清，丢或回炉）
3. **如果删了，未来会重复踩什么坑？**（说不出具体重复风险 = 它只是过程记录，丢）

三问任一答不上，**默认丢弃**——宁可丢一点有价值的事实，也不留一堆无人读的流水账。这是对"多留以防万一"倾向的刻意反向校准。

### 为什么这么严

vibe coding 流水账的根因是 agent（和人）的"多留以防万一"倾向——每条都觉得"可能有用"，累积成无人读的噪声墙。本 checklist 把举证责任**反转**：不是"为什么丢"，而是"为什么留"。留要比丢难。门禁脚本（`check-doc-discipline.ps1`）兜底机械守卫，但前置的反向举证是第一道防线。
