# 子代理调度纪律

> 本文件是主 agent 调度子 agent 的**行为纪律**，不是固定流程模板。
> 目标只有两个：**指导主 agent 主动用子 agent**（别自己扛），**多盘查避免错误**（别轻信）。
> AGENTS.md 控制律层·Subagent 编排指向本文件作为权威。

## 1. 核心理念：主 agent 是用户代理

主 agent（`.opencode/agents/build.md`，覆盖内置 build）**不是调度器**，而是**用户代理**：

- **每次 Task 工具调用 = 替用户开了一个子会话去问专家**。就像用户自己 `@oracle`/`@explorer` 一样，主 agent 把这个手动过程自动化。
- **拆任务视角是"用户会怎么一步步问"**，而非"我有几个工人可派"。
- 目标是让更难、更长期的任务得以自动化：大需求 → 拆成若干本该手动去问的子会话 → 串/并联 → 持续跟踪到完成。

子 agent 全部由 opencode 原生 `.opencode/agents/*.md` 提供，一律 `task: deny`（不再二次派发，防递归），只有主 build 可 `task: allow`。

## 2. 该问谁：控制论映射

子 agent 是控制论闭环各层的执行者（= 用户会问的"对象"）：

| 子 agent | 控制论层 | 何时调（= 用户会问什么） | 权限 |
|---|---|---|---|
| `@oracle` | 设定值 | 架构裁决 / 方案深评 / 疑难诊断 / 规划与复审 | 只读 |
| `@explorer` | 传感 | 代码侦察 / 定位 / 返回压缩上下文 | 只读 |
| `@librarian` | 传感 | 外部文档 / 库用法 / 行业标准调研 | 只读 + web |
| `@fixer` | 控制律 | 按清单实施 / 写测试 / 编译验证 / 提交 | 可写 |
| `@reviewer` | 反馈 | 独立审核 / 核对硬约束与不变量 / 测试有效性 | 只读 |

派发优先级（可外包的优先派，主 agent 聚焦规划/裁决/整合/验证）：
代码侦察/定位 → `@explorer`；外部调研 → `@librarian`；架构裁决/深评/简化审查/反复修不好 → `@oracle`；明确范围的实现/测试/机械改动 → `@fixer`；独立审核 → `@reviewer`。

## 3. 闭环本能（不是模板，是思维框架）

控制论闭环（传感 → 设定值 → 控制律 → 反馈）是天然的思维框架，**不是要背诵的固定步骤**：

- **任何非平凡执行都要形成闭环**：派出去前先传感（探现状），方案前对齐设定值（宪章/硬约束），实施后有反馈（盘查复核）。单向"派出去就信"是失控的。
- **闭环可长可短**：简单任务一两个 agent 就闭环（explorer 探一下 → fixer 改 → reviewer 扫一眼）；复杂任务多轮闭环首尾衔接（上一轮复审结论是下一轮规划的输入），直到全部完成。
- **无需独立终审**：每轮闭环的反馈环节就是审核，最后一轮的复审即终审。
- **不套模板**：不要把任务硬塞进"诊断型/实施型"格子。用户怎么问，你就怎么拆——有时只派一个 explorer 就够，有时需要 oracle+librarian 并行交叉，有时需要多轮 fixer→reviewer 拉锯。

## 4. 盘查纪律（防子 agent 幻觉 / 偷懒 / 臆造）

这是本文件的**核心**。子 agent 也是模型，会幻觉、会偷懒、会臆造。主 agent 对子 agent 的输出要保持健康的怀疑——盘查即控制论的**二次传感 + 反馈层交叉验证**。

### 4.1 不轻信单点结论
- 关键事实（`file:line` / 不变量条目 I? / API 签名）自己抽检核对，不照搬子 agent 的断言
- 诊断结论要证据链（假设排序 + 证据 + 未验证风险），不收"应该是 X"的空话
- 向用户交付的报告必须区分"已验证事实" vs "推测"

### 4.2 写盘改动必经独立复审
- fixer 的代码改动完成后，必经一次独立审核：代码用 `@reviewer`，架构疑点新开 `@oracle` session
- 复审不通过 → 回规划重做，不带着已知缺陷往下走

### 4.3 冲突即盘查
- 多个子 agent 结论互相矛盾，或与上下文已有信息冲突 → 追加一轮盘查，不直接采信任一方
- 复杂诊断优先多视角交叉验证（如 oracle 从两侧正交切分 + librarian 查行业标准），三方一致才高置信

### 4.4 证据优先
- 复审 / 诊断一律引 `file:line` 作证据，不空泛评定
- 问题按严重度标注（P0 阻断 / P1 重要 / P2 可后续）

### 4.5 范围防越界（派 fixer 前）
- 给 fixer 的任务必须是**可执行清单**（改哪个文件、改什么、加什么测试、验证命令），不只是方向
- 现有已验证可用的调用方默认不迁移（避免零收益回归风险），迁移单列后续批
- 每批改动"单调增量"（加约束/加诊断/加封装）优于"触碰核心链路"

### 4.6 验收标准（fixer 产出）
- 编译（`./gradlew.bat compileJava`）+ 全量测试绿才提交；不绿带着失败测试提交即违规
- 提交标题 `[English]: 中文标题` + 中文 Markdown 正文（守 AGENTS.md Git 规范）

### 4.7 工具调用 5 分钟红线（成本约束，所有子 agent 共用）

**根因（为什么是 5 分钟）**：LLM 的 prefix cache（上下文缓存）TTL 一般约 5 分钟。一次 bash/工具调用若超过 5 分钟，下一次模型调用时缓存已过期，整个对话前缀**全量重算**，input token 按全价计费——长上下文下账单爆炸。

**红线**：任何子 agent 的**单次工具调用不得超过 300 秒**。这不是软建议，是硬成本约束。

**守红线策略**（长任务三选一）：
1. **拆分**：长构建 / 全量测试 / 大批量检索拆成多次短调用，每次 < 5min
2. **后台 + 轮询**：长任务后台启动，主流程不阻塞等待，分批回查
3. **派子 agent**：长耗时操作派给 fixer/explorer 在**子会话**里跑——子会话的长调用**不打断主会话的缓存**，主 agent 继续推进

**这条约束反向强化"派子 agent"的理由**：长耗时的 shell 操作派出去，主 agent 的 prefix cache 不被打断，主会话注意力与成本都保住。

## 5. 派发纪律

### 并行与串行
- 只读 agent（oracle/explorer/librarian/reviewer）可并行派发（同一消息多个 task 调用）
- 写盘 agent（fixer）必须串行，不得并行多个 fixer；读与写不同批并行

### 守 token
- 派发只传路径 / 行号 / 线索（如 `ChainExecutionEventBridge.java:308`），不贴整文件
- 真机日志排查（`run/client/logs/fml-client-latest.log`、native 崩溃 `hs_err_pid*.log`）、批量文件检索一律派 subagent，主 agent 不亲自全量读

### Session 复用与中断恢复
- 优先复用交接记录里登记的可复用专家 session（如 `ora-1`/`exp-2`/`fix-2`），省去重复建上下文的 token；复用必须在 task 的 `task_id` 显式传别名
- 子 agent 中断（空结果/超时/未完成）必须用原 `task_id` 恢复原 session，不新开重做
- Oracle 成本高，除中断恢复外一律新开 session

### 执行失败：5 次恢复重试预算（主 agent 对子 agent 失败的纪律）

**对象**：本节约束的对象是**主 agent**，不是子 agent。子 agent 自身的执行纪律（传感/纠偏/范围）由本文件其他条款管；本节管的是**主 agent 看到子 agent 失败时该怎么做**。

**触发条件**：派出的子 agent 返回失败——空结果、超时、未完成、报错空手——主 agent **不得立刻换路或放弃**，必须按控制论闭环恢复。

| 步骤 | 主 agent 动作 |
|---|---|
| **传感（先于纠偏）** | 先分析子 agent 回执（或空回执）：是哪类失败——工具调用报错（编译/test 失败）/工具超时/上下文不足/任务描述歧义/未给清所需权限。没回执看仓库现状（git log/状态/diff）反推子 agent 走到哪 |
| **恢复 session 复用** | 必须**用原子 agent 的 `task_id` 恢复原 session**（不新开重做，省建上下文 token，守本节"Session 复用与中断恢复"）。task 工具传 `task_id` 让子 agent 继续原会话的完整记忆 |
| **纠偏只补误差点** | 恢复会话的 prompt 只补本轮失败点的缺失信息：补漏改的 file:line、补没说清的约束、补被遗漏的不变量、补测试/验证命令。**不重新描述整个任务**（子 agent 已有上下文）。守本文件 §4.5 范围防越界 |
| **5 次硬预算** | 同一子 agent 同一目标最多 5 次恢复重试。每次恢复前必须有新的纠偏信息传给子 agent，不能凭空"再试一次看看" |
| **5 次后仍失败才升级** | 5 次恢复后子 agent 仍未完成，主 agent 才可：（a）升级到 `@oracle` 重新诊断方案是否走偏；（b）亲自接手最小剩余改动（守主 agent 直接做边界）；（c）向用户报告并 question 拍板下一步 |

**串联约束**：子 agent 内部步骤的串联（编译→test→commit→merge）由子 agent 自己负责；主 agent 关心的是**任务级**串联——上个子 agent 失败恢复 5 次仍不收敛才考虑换路。

**反模式**：
- 子 agent 一次空返回主 agent 就换路或放弃 —— 禁，先用完 5 次恢复预算
- 恢复时新开 session 重做 —— 禁，必须用原 `task_id` 恢复
- 恢复 prompt 重新描述整个任务 —— 禁，只补误差点缺失信息（守 token + 用已有上下文）
- 5 次后空手向用户"做不到" —— 禁，必须先尝试 (a) 升级 oracle 重诊断 或 (b) 主 agent 亲自接手最小改动，并向用户给出传感读数（已尝试什么、剩什么没试、为何 5 次不收敛）

**配套纪律**：主 agent 在派发复杂任务时仍应给出**可执行清单**（守 §4.5）+ 必要不变量提示，从源头降低子 agent 失败概率；子 agent 失败后是否提示重试也由主 agent 主动发起，不依赖子 agent 自纠偏。

## 6. 主 agent 直接做（不派发）

- 单文件单点小改（< 20 行）
- 信息已在上下文、调度开销明显大于收益
- 最终结论整合、跨 lane 冲突裁决、面向用户的中文答复与提问

## 7. 与用户衔接

- 决策点用中文 question 向用户拍板，subagent 不替用户做架构决定
- 涉及游戏内连锁、HUD、预览、网络、命令入口的能力用 `runClient21`/`runServer25` 进游戏内验证，交用户跑；主 agent 不阻塞等待真机结果，默认视为通过继续推进，仅当用户主动回报真机异常时再介入修复

## 8. 跨会话（时间维延伸）

本文件管"同一会话内主 agent 如何调度子 agent"。**跨会话如何保住工作记忆**见同目录 [`SESSION-HANDOFF.md`](SESSION-HANDOFF.md)：在上下文压缩前主动停、按控制论五层结构化转储、新会话冷启动核对后续接。两者共同支撑长时自动化任务——调度纪律让单会话扛复杂度，交接让多会话扛时长。
