# 代码框架设计风险排查报告

> 审查日期：2026-05-28  
> 审查范围：全项目（`MyMod`、`chain/`、`compat/`、`network/`、`mixins/`、`event/`、`parallel/`、`client/`）

---

## 一、严重风险（S1-S5）

### S1：Worker 线程并发读取 Minecraft 世界状态

- **状态**：已知架构取舍，当前版本接受该风险，暂不调整。
- **位置**：`ChainSearchContext` 持有 `World` 引用 → `ChainPlanningRuntimeFactory.createSearchContext()` → `ChainCandidateFilter` → `traverser.step()` → `blockMatcher.matches()`
- **描述**：`ParallelTickExecutor` 的 worker 线程通过 `World.getBlock()` / `getTileEntity()` 直接访问 MC 世界状态，而 Chunk 加载/卸载、方块修改、TE 更新全部发生在主线程
- **后果**：可能触发 `ConcurrentModificationException`、读取半初始化区块数据、C2 级崩溃
- **建议**：制作世界状态的不可变快照，或在主线程执行世界读取

### S2：掉落缓冲无容量上限 + 单 Tick 全量释放

- **状态**：已知策略取舍，当前保留聚合后单次释放行为，暂不调整。
- **位置**：`ChainPlayerDropBuffer` 使用无界 `ArrayList<ItemStack>`；`ChainDropReleaseHelper.releaseAtCoordinates()` 一次性生成全部 `EntityItem`
- **后果**：大量连锁（如巨树）积累数百个掉落物后在同一 tick 全部释放 → Tick 延迟飙升，TPS 降到个位数
- **建议**：添加上限（如 500）、分批释放（每 tick 100 个）

### S3：网络包缺少上限校验（安全漏洞）

- **状态**：已修复。服务端入包阶段已按 `Config` 上限夹紧半径和数量请求。
- **位置**：`PacketChainConfigRequest` 对 `requestedChainRadius` / `requestedChainMaxBlocks` 无上限；`PacketLootGamesMinesweeperPreviewRequest` 对 `radius` / `maxTargets` 无上限
- **后果**：恶意客户端可发送极大值，导致服务端 CPU/内存爆炸 → DoS 攻击向量
- **建议**：与 `Config` 中的对应上限做 `Math.min` 绑定

### S4：客户端 GPU 资源 dispose() 从未调用

- **状态**：已修复。客户端断线与客户端世界卸载时会停止预览任务并释放 GPU 缓存。
- **位置**：`ChainPreviewMeshCache.dispose()` 已定义但全项目无调用点
- **后果**：VAO/VBO/CBO/EBO 在退出世界后永远泄漏，热重载场景下累积
- **建议**：在 `ClientProxy` 或 `ChainPreviewRenderer` 中添加 `onClientDisconnect` / `onWorldUnload` 回调

### S5：GregTechCableCompatAdapter 直接访问 GT 内部 API

- **位置**：`GregTechCableCompatAdapter.replaceCableKeepingConnections()` 直接访问 `baseMetaPipeEntity.mConnections`；`createCableFromStack()` 调用 `gregtech.common.blocks.ItemMachines.getMetaTileEntity()`
- **后果**：GT 版本升级 → 编译失败或运行时数据损坏
- **建议**：改用 GT 公开 API 方法，或为内部访问添加 try-catch 降级

## 二、高风险（H1-H9）

### H1：规划核心 Lambda 无 try-catch

- **位置**：`AbstractFloodFillPlanningStrategy.startPlanningInternal()` Lambda 回调（约 79-142 行）
- **描述**：`traverser.step()` 在 worker 线程中执行，无异常保护
- **后果**：异常传播到 `ParallelTickExecutor` 兜底 catch → 整个规划任务静默终止，target 丢失
- **建议**：在 Lambda 内部添加 try-catch，异常时标记 planner 失败并记录日志

### H2：执行器 while 循环无 try-catch

- **位置**：`ChainExecutor.onServerTick()` while 循环中 `actionExecutor.canExecute()` / `execute()`
- **后果**：一个 target 异常 → 循环 break，剩余所有 target 丢失
- **建议**：在 while 循环内添加 try-catch 包裹单个 target 的处理

### H3：ParallelTickExecutor 主线程阻塞 + 潜在死锁

- **位置**：`ParallelTickExecutor.endStage()` 中 `waitForMinimumWindow(15ms)` + `workersIdle.await()`
- **描述**：15ms 占单个 Tick 预算的 30%；若 worker 线程分片内访问需主线程同步的 MC API，则与等待的 endStage 形成死锁
- **建议**：评估降低默认 `parallelTickMinDurationMs`；在 `ParallelTickTask` 文档中显式声明线程安全约束

### H4：客户端预览 currentTarget 跨线程无同步

- **位置**：`ChainPreviewController.currentTarget`（第 45 行）非 volatile
- **描述**：客户端线程写入，Worker 线程通过闭包读取
- **后果**：JVM 可能无限缓存旧值 → worker 处理废弃预览或提前终止有效预览
- **建议**：声明为 `volatile` 或使用 `AtomicReference<ChainTarget>`

### H5：反射适配器无 Method/Field 缓存

- **位置**：`ReflectiveGregTechTileIdentityCompatAdapter.invoke()` 和 `ReflectiveFieldTileIdentityCompatAdapter.readIntField()` 每次调用都执行 `getMethod()` / `getField()` 反射查找
- **后果**：高频匹配场景下显著反射性能开销
- **建议**：缓存 `Method` / `Field` 到实例字段或 Map

### H6：LootGamesMinesweeperCompatAdapter 编译期硬依赖

- **位置**：`LootGamesMinesweeperCompatAdapter` import 了 10 个 LootGames 类
- **后果**：构建环境中无 LootGames jar → 编译失败（其他适配器均为反射可选加载）
- **建议**：改为反射方式加载，使其与其他适配器一致

### H7：ChainSession 暴露可变 runtimeState

- **位置**：`ChainSession.getRuntimeState()` 返回可变 `ChainRuntimeState` 对象引用
- **后果**：外部可绕过 Session 生命周期直接修改运行时状态，破坏封装
- **建议**：将 `ChainRuntimeState` 从 Session 中分离到 `ChainPlayerState` 直接管理

### H8：GT 线缆锁定 Map 无过期清理

- **位置**：`GregTechCableSessionState.LOCKED_REPLACEMENT_META_TILE_IDS` 静态 `ConcurrentHashMap<UUID, Integer>`
- **描述**：仅在 `clear(session)` 时删除条目，玩家异常下线则永久泄漏
- **后果**：长期运行服务器积累僵尸条目；UUID 重用时旧值被错误复用
- **建议**：添加基于玩家下线事件的自动清理机制

### H9：BoxScanTraverser 一次性装填候选点

- **位置**：`BoxScanTraverser.enqueueNextShell()` 将 `~24R²` 个候选点一次性加入队列
- **后果**：R=64 时约 98000 个候选点 → 瞬时内存峰值和 GC 压力
- **建议**：改为分批装填或限制每次装填数量

## 三、中风险（M1-M17）

### M1：EventBus 遍历与注册并发风险

- **位置**：`EventBus.post()` 加锁取 List 引用 → 解锁后遍历同一个 `ArrayList`
- **描述**：另一线程同时 `register()` 修改该列表 → 理论上的 CME
- **建议**：遍历时做防御性拷贝 `new ArrayList<>(list)` 或全程持锁

### M2：EventBus 监听器无弱引用清理

- **位置**：`EventBus.listeners` Map 持有 `EventListener` 强引用
- **描述**：依赖调用方手动 `unregister()`，遗漏则内存泄漏
- **建议**：文档中强调生命周期管理要求

### M3：EventBus 每次注册全量排序 O(n log n)

- **位置**：`EventBus.sortListeners()` 在每次 `register()` 时调用
- **建议**：改用二分插入维护有序列表

### M4：ParallelTickExecutor tickWindowOpen 的 TOCTOU

- **位置**：`runSlicesInCurrentTick()` 中 volatile 检查到 enterWorker 之间窗口可能关闭
- **影响**：最多一次多余分片执行，不影响正确性

### M5：ChainStateService 职责过重（God Class）

- **位置**：277 行，包含状态 CRUD + 事件处理 + 网络同步 + 掉落清理 + 客户端状态
- **建议**：拆分为 `ServerStateService` + `ClientStateAdapter` + `DropFlushManager`

### M6：ChainSession 构造器链过长

- **描述**：4 个重载构造函数（4→5→7→9 参数）
- **建议**：使用 Builder 模式

### M7：规划策略无显式结果传递

- **位置**：`ChainPlanningStrategy.startPlanning()` 无返回值、无回调
- **描述**：通过队列副作用隐式传递结果
- **建议**：加入 `Consumer<ChainPlan>` 参数或返回 `Future`

### M8：PacketKeyState 无效 keyId 日志膨胀

- **位置**：恶意客户端可大量发送无效 keyId 造成 debug 日志暴涨
- **建议**：添加 keyId 范围校验

### M9：MixinTileEntityOres @Redirect + FIELD + ordinal 依赖

- **位置**：重定向 `mNatural` 字段的 ordinal=0 和 ordinal=1 访问
- **风险**：GT 重构方法体 → 注入到错误位置
- **建议**：考虑 `@ModifyVariable` 替代方案

### M10：MixinTickEvent 注入点密集

- **位置**：`FMLCommonHandler` 四个 tick 方法 × HEAD+TAIL = 8 个注入点
- **风险**：与性能分析模组可能冲突
- **建议**：评估是否需要所有 8 个点

### M11：兼容层类名硬编码 + 静默失效

- **位置**：`CompatAdapters` 22 个完全限定类名；`ClassNameCompatSupport.resolveClass()` 失败无日志
- **建议**：添加 debug 级别日志

### M12：NamedClassOreCompatAdapter / NamedClassCropCompatAdapter 92% 重复

- **建议**：提取泛型基类

### M13：FortuneCompatHelper 两个 resolve 方法 80% 重复

- **建议**：提取公共逻辑，参数化增量

### M14：ChainPlayerDropBuffer.add() 修改传入 ItemStack

- **描述**：`drop.stackSize += ...` 对传入对象有副作用
- **建议**：在方法文档中注明，或改为返回新对象

### M15：HudOverlay 使用弃用 API

- **位置**：`new ScaledResolution(mc, mc.displayWidth, mc.displayHeight)` 已弃用
- **建议**：改用 `event.resolution`

### M16：GPU 缓冲扩容后永不缩容

- **位置**：`ChainPreviewMeshCache.calculateNewCapacity()` 可逆但无缩容路径
- **建议**：闲置超过 N 帧后重建为最小容量

### M17：PlayerManager.clearAllPlayers() 隐式语义依赖

- **位置**：`MixinMinecraft` 中 `worldClientIn == null` 触发清理
- **描述**：其他触发出主菜单的路径可能漏清理

## 四、低风险（L1-L11）

| # | 模块 | 位置 | 风险描述 |
|---|------|------|---------|
| L1 | Config | `public static` 字段 + 无私有构造器 | 非严格单例 |
| L2 | ChainPlan | 构造函数未 null 检查 origin | 延迟 NPE |
| L3 | ChainSearchContext | `confirmedCount` 为非 volatile int | worker 线程可见性 |
| L4 | ChainRuntimeState | 两组 volatile boolean 非原子组合 | 极短不一致窗口 |
| L5 | 规划层 | `nextFrontier` 规划完成后未清空 | 不一致清理模式 |
| L6 | 执行层 | target 异常后不重试 | 暂时性异常丢失 |
| L7 | 掉落系统 | `discard()` 静默丢弃无玩家通知 | 玩家困惑 |
| L8 | 客户端 | `specialPreviewRequestId` int 无溢出保护 | 极端频率碰撞 |
| L9 | PlayerManager | 无 unregister() | 热重载场景泄漏 |
| L10 | EtFuturum适配器 | `endsWith("_ore")` 启发式匹配 | 理论误匹配 |
| L11 | MixinTickEvent | beginStage/endStage 配对依赖 executor 保护 | 异常时状态不一致 |
