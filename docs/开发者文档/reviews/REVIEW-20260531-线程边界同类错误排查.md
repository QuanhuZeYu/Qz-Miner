# Review: 线程边界同类错误排查

## 范围

- issue `#234` 同类问题专项排查
- 客户端 OpenGL 调用点
- `SimpleNetworkWrapper` 全部消息处理器
- 自定义玩家断线清理链路

## 主要发现

### 1. 服务端扫雷预览请求包直接在网络线程读取世界状态

- 位置：`src/main/java/club/heiqi/qz_miner/network/PacketLootGamesMinesweeperPreviewRequest.java:64-79`
- 位置：`src/main/java/club/heiqi/qz_miner/compat/adapter/lootgames/LootGamesMinesweeperCompatAdapter.java:115-200`
- 说明：`onMessage(...)` 里直接用 `player.worldObj` 调 `collectBombTargets(...)`，后者继续调用 `world.getTileEntity(...)`、`world.getBlock(...)`、`world.getBlockMetadata(...)`。
- 结论：这是与 issue `#234` 同类的线程边界错误，只是对象从 OpenGL 上下文换成了 Minecraft 世界对象。消息处理器没有任何主线程调度，理论上会把世界读取放到 Netty 线程执行。

### 2. 客户端状态同步包直接在 Netty 线程修改本地状态

- 位置：`src/main/java/club/heiqi/qz_miner/network/PacketChainStateSync.java:69-90`
- 位置：`src/main/java/club/heiqi/qz_miner/ClientProxy.java:39-52`
- 位置：`src/main/java/club/heiqi/qz_miner/chain/state/AbstractChainModeState.java:15-17,31-45`
- 说明：`PacketChainStateSync.Handler.onMessage(...)` 直接调用 `MyMod.proxy.handleClientChainStateSync(...)`；客户端代理实现没有调度回主线程，而是立即写入 `ChainClientState` 与其父类 `AbstractChainModeState` 的普通字段和 `EnumMap`。
- 结论：这是确认存在的同类问题。虽然当前不会像 OpenGL 那样立刻 native crash，但它依然把客户端主线程状态修改放到了 Netty 线程，存在数据竞争和状态撕裂风险。

### 3. 其余服务端消息处理器也没有主线程收口，存在同类架构风险

- 位置：`src/main/java/club/heiqi/qz_miner/network/PacketKeyState.java:55-63`
- 位置：`src/main/java/club/heiqi/qz_miner/network/PacketChainModeSwitch.java:37-49`
- 位置：`src/main/java/club/heiqi/qz_miner/network/PacketChainSubModeSwitch.java:45-57`
- 位置：`src/main/java/club/heiqi/qz_miner/network/PacketChainConfigRequest.java:45-62`
- 位置：`src/main/java/club/heiqi/qz_miner/chain/state/ChainStateService.java:86-220`
- 说明：这些 `onMessage(...)` 都直接调用 `ChainStateService`，其中包含状态切换、停止执行、同步玩家状态、注销并行任务等逻辑，但没有统一调度到服务端主线程。
- 结论：这一组属于与 issue `#234` 相同的根因类型，即“网络线程直接触碰主线程语义对象”。其中有些路径当前只改 `volatile` 字段，表面风险较低；但 `stopPlayerExecution(...)`、`syncPlayerState(...)` 等路径已经明显超出简单字段写入范围。

### 4. 自定义玩家断线清理链路缺少显式线程边界保护

- 位置：`src/main/java/club/heiqi/qz_miner/mixins/early/MixinNetHandlerPlayServer.java:20-28`
- 位置：`src/main/java/club/heiqi/qz_miner/core/PlayerManager.java:122-128`
- 位置：`src/main/java/club/heiqi/qz_miner/chain/state/ChainStateService.java:223-275`
- 位置：`src/main/java/club/heiqi/qz_miner/chain/executor/ChainDropReleaseHelper.java:160-170`
- 说明：`PlayerDisconnectEvent` 在 `NetHandlerPlayServer.onDisconnect(...)` 的 HEAD 注入点直接广播，后续会进入 `cleanupPlayerState(...)`，再可能调用 `world.spawnEntityInWorld(...)` 释放掉落。当前整条链路没有任何显式主线程收口。
- 结论：这条问题链与 issue `#234` 的形态高度相似，但是否一定复现取决于 `NetHandlerPlayServer.onDisconnect(...)` 的实际调用线程。现阶段应视为高风险待确认项，而不是已证明的崩溃点。

## 排查结论

- 未发现第二处独立的 OpenGL 调用模块；仓库里的 OpenGL 调用集中在 `ChainPreviewRenderer` / `ChainPreviewMeshCache`。
- 但“错误线程直接执行主线程语义逻辑”这一类问题并不只存在于 issue `#234`，而是系统性存在于网络消息处理层。
- 当前 6 个消息处理器里，只有扫雷预览响应最终通过 `ClientProxy.handleClientLootGamesMinesweeperPreview(...)` 调度回了客户端主线程；其余处理器都缺少统一线程收口。

## 建议顺序

1. 先修 `ClientConnectionListener` 的 OpenGL 清理线程问题，解决已知闪退。
2. 再统一收口全部 `SimpleNetworkWrapper` 处理器：客户端包调度到客户端主线程，服务端包调度到服务端主线程。
3. 最后复核 `PlayerDisconnectEvent` 链路，避免掉落释放和状态清理在潜在错误线程执行。
