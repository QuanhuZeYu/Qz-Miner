# 连锁会话与掉落缓冲耦合导致概率吞掉落

## 错误现象

- 连锁基础模式、爆破矿石模式在 GTNH 2.8.4 中使用镐子、锤子等工具时，存在概率性吞掉落。
- 表现通常为：方块已经被破坏，但对应产物没有正常掉落到世界中。

## 触发场景

- `CHAIN` 或 `AREA` 相关挖掘模式触发 `HarvestDropsEvent` 聚合掉落。
- 掉落已被缓存，但在 `WorldTick` 统一释放前，会话被重启、停止或被生命周期清理打断。
- 高风险场景包括：
  - 快速连续触发下一次连锁
  - 松键、切模式、切子模式
  - 玩家重生、切维度、退出世界

## 根本原因

- 旧实现把掉落缓冲放在 `ChainRuntimeState.pendingDrops` 中。
- `ChainRuntimeState` 又绑定在单次 `ChainSession` 上。
- 掉落释放依赖旧 `session` 在执行结束后继续存活到 `WorldTick`。
- 一旦旧 `session` 被清理，`pendingDrops` 就会随运行态一起被清空。

## 修复方案

- 引入玩家级掉落缓冲：`ChainPlayerDropBuffer`
- 将掉落缓存从 `ChainRuntimeState` 解耦到 `ChainPlayerState`
- `ChainDropCollector` 改为直接读写玩家级缓冲
- 生命周期清理统一增加掉落释放兜底：
  - 优先当前玩家位置
  - 回退到重生点或世界出生点
  - 必要时使用已缓存的兜底坐标

## 预防措施

- 不要把玩家资产级缓存绑定到单次会话运行态上。
- `ChainSession` 只负责请求参数与一次执行过程，不承担跨会话资产缓存职责。
- 设计延迟释放资源时，必须先明确“宿主是谁”和“宿主提前结束时如何兜底”。
- 后续若新增类似“延迟结算、延迟释放、延迟落地”的机制，优先挂到玩家级或全局级稳定宿主，而不是挂到单次 `runtimeState`。
