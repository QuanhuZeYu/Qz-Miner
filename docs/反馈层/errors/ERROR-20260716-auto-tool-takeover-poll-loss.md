# 连锁工具耗尽时 poll 先于执行门导致目标丢失

## 错误现象

普通 CHAIN/AREA 执行先 `poll()` 再检查当前工具，剩余耐久降到 1/0 后队首被记为已消费；后续目标也可能随正常收口一起丢失。

## 触发场景

连锁已进入 FROZEN/RUNNING，当前主手在执行途中耗尽，而库存仍有可采掘同一服务端目标的候选工具。

## 根本原因

瞬时资源门位于破坏队列消费之后，且协议 v2 没有同 round TAKEOVER/DECLINE 事务，服务端无法在保留队首时等待客户端选候选。

## 修复方案

协议 v3 增加固定帧目标请求和动作 6/7。执行桥在 `peek()` 后调用服务端主线程协调门：WAIT 保留队首，APPLIED 后才 `poll()`，DECLINE、拒绝、超时或生命周期失效走既有事件收口。已有 ledger 的接替使用一次三槽引用轮转。

## 预防措施

测试同时断言 gate 的源码顺序、pending 幂等/超时、DECLINE 零库存访问、双槽/三槽引用守恒与最终 RESTORE 可逆；新增异步执行资源门时统一遵守“peek → gate → poll”。
