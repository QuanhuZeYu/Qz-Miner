# Issue 诊断支持政策

## 决策

玩家提交 Issue 时只提供两项输入：用自己的话描述“遇到了什么问题”，并上传对应的最新日志。客户端或单人游戏上传 `run/client/logs/fml-client-latest.log`，服务器问题上传 `run/server/logs/fml-server-latest.log`；文件太大可压缩为 zip，不知道选哪个时上传手边最新日志即可。图片和视频可选。

维护者负责根据症状分析日志并路由到现有诊断 marker，玩家无需筛 marker、分析日志、填写环境矩阵、整理完整复现步骤或执行测试。初步证据不足时，维护者应围绕该 Issue 先评估最小埋点补强，再按需提出一个具体补充请求。内部症状路由以 `docs/控制律层/稳定命令.md` 为准。

## 原则

- **两项输入**：问题描述与对应日志是统一入口；图片、视频仅作可选补充。
- **维护者路由**：由维护者判断客户端、服务端、GregTech 或 native 日志中哪一项与症状相关。
- **维护者分析**：日志时段、marker 与根因判断均由维护者完成，不转交玩家。
- **按需单点追问**：现有日志仍不足时，只追问当前判断所缺的一个关键信息。
- **隐私最小化**：不默认索取客户端与服务端双侧日志、环境清单、NBT 或与问题无关的信息。

## 边界

本政策不减少项目自身的自动化、CI 与维护者验证责任，也不承诺仅凭一句描述一定能完成根因定位。现有日志出现具体盲区时，再围绕该 Issue 评估最小诊断补强，不预先把采集成本转嫁给所有玩家。
