# 决策：记忆框架适配 CodeGraph MCP

## 背景

项目已经建立仓库内分层 AI 记忆框架，但 Qz-Miner 的连锁执行、并行 Tick、兼容适配、网络包和客户端预览链路会持续变化。纯靠手工维护类清单、调用关系和影响面容易过期。

CodeGraph MCP 可以在 opencode 中提供本地代码图谱、符号搜索、调用关系、影响分析和相关测试查询。需要明确它与仓库记忆文档的职责边界，避免再次把动态代码关系堆回 `docs/AI记忆文档.md` 或长期事实文档。

## 候选方案

1. 继续只用 Markdown 记忆文档和 Glob/Grep/Read，所有代码关系由 Agent 每次现查
2. 把 CodeGraph 查询结果定期导出为仓库内索引文档，后续 Agent 直接读索引
3. 将 CodeGraph 作为动态代码关系查询层，Markdown 记忆只保存稳定事实、决策和写回规则

## 最终选择

选择方案 3：CodeGraph MCP 只承担动态代码关系查询，仓库内记忆框架继续承担稳定协作记忆。

具体落地为：

- 新增 `docs/记忆/长期事实/CodeGraph协作.md`，记录 CodeGraph MCP 的使用边界、读取流程和写回规则
- `docs/AI记忆文档.md` 和 `docs/记忆/README.md` 只增加入口和流程提示，不承载代码图谱结果
- 需要具体类、方法、调用链、影响面时，优先让 CodeGraph 缩小范围，再用源码和测试确认
- CodeGraph 查询形成长期稳定结论后，仍按既有分层写回对应文档

## 选择原因

- 动态代码关系最容易过期，适合交给可重新索引的 MCP，而不是写成静态清单
- Markdown 记忆仍保留版本控制、审查和多人协作优势
- 避免 `docs/AI记忆文档.md` 重新膨胀为总知识库
- 保留 Glob/Grep/Read 和源码测试作为最终事实校验，降低静态索引误判风险
- CodeGraph 的调用图和影响分析可以减少跨包重构前的重复探索成本

## 影响范围

- 后续涉及跨类、跨包、调用链、影响面和相关测试的问题，应优先考虑使用 `codegraph` MCP 查询
- 记忆文档不新增大段类清单、调用图导出或一次性 CodeGraph 查询结果
- 重要发现仍按当前态、长期事实、决策、错误记录和审查记录分层写回
- opencode 项目配置变更后，正在运行的会话需要重启才能使用新 MCP

## 后续注意事项

- CodeGraph 结果必须经过源码读取或测试验证后才能作为实现依据
- MCP 未加载、索引过期或查询结果异常时，立即回退到原有工具链
- 不向 CodeGraph memory 工具写入密钥、账号、私有地址或未经确认的推断
